# 핸드오프 — 복구했는데 claude 가 일부만 살아난다

작성 2026-09-10 · 앞 세션 `b52d59f0`(history viewer 폴더 `⚙️ cmux`)

## 증상 (사용자 신고)

스냅샷 #48494(09-09 03:27)에서 **INBOX 그룹(워크스페이스 24개)** 을 복구했더니
**세 개만** claude 가 떴다 — `Two Mac Claude 연속성` · `Korea FDE Group 카톡방` ·
`cmux에서 Claude code 세션 자동 종료 확인`. 나머지는 **빈 터미널(`~`)로 레이아웃만** 복구됐다.
화면 안내는 "최대 12개 자동 실행"이었으니 사용자는 12개를 기대했다.

사용자 말: *"예전에도 그런 적이 있었는데, 그때 조치한 걸로 강건한 조치가 되지 않았나봐."*

## claude 주입을 막는 게이트는 **두 개**다

| | 위치 | 내용 |
|---|---|---|
| ① 배치 상한 | `restore.py:22` `MAX_CLAUDE_AUTORUN = 12` | 한 번의 복구에서 claude 는 **총 12개**까지. OOM 가드 |
| ② 이미 실행중 제외 | `restore.py:123~124` (`do_ar` 조건) | `sid` 가 `running_sids` 에 있으면 **command 를 안 넣는다**(같은 .jsonl 에 claude 둘 = 충돌) |

②의 판정은 `cmux_client.running_claude_sids()`(`cmux_client.py:476`) — **`ps` 에서 `--resume <uuid>` 를 긁는다.**
복구 시작 전 1회 스냅샷이고, 복구 중 주입한 sid 는 집합에 더해 같은 배치 내 중복을 막는다.

신고 당시 복구표에 **「실행중」 62개**가 찍혀 있었다. 24개 중 21개가 ②에 걸렸다면 3개만 뜬 것이 설명된다.
**즉 ①(상한 12)이 아니라 ②가 범인일 가능성이 높다.** 먼저 이걸 가른다.

## ★ 가장 유력한 가설 — «프로세스가 살아 있다»와 «내가 닿을 수 있다»는 다르다

`running_claude_sids()` 는 **프로세스만** 본다. 그런데 이 저장소는 이미 반대편에서 그 간극을 알고 있다 —
`nav.py` 가 *"탭을 못 찾아 목록에서 제외한 claude N개 — 탭이 이미 닫혔는데 프로세스가 남았거나…"* 라는
경고를 띄운다. **탭 없이 프로세스만 살아 있는 claude 가 실재한다는 뜻이다.**

그 상태의 세션은 사용자가 **접근할 방법이 없다.** 복구는 바로 그걸 되살리려는 행위인데,
②는 "프로세스가 있으니 실행중"이라며 건너뛴다 → **되살리려던 것이 정확히 안 되살아난다.**

→ **첫 번째로 확인할 것**: 안 뜬 워크스페이스들의 sid 가 그 시점에 **cmux 탭을 갖고 있었는지**.
   `/api/nav` 의 `located` 필드·경고 문구와 `ps` 결과를 나란히 놓으면 갈린다.
   탭이 없는데 「실행중」으로 세고 있었다면 ②의 판정 기준을 «프로세스 생존»에서
   «탭이 있고 살아 있음»으로 좁혀야 한다.

## 그 밖에 확인할 것

1. **안내가 절반만 있다.** `static/index.html:1058` 은 *"최대 12개 자동 실행, 초과분은 복구표에서 수동"* 만
   말하고 **②는 한마디도 없다.** 응답에 `autorunInjected` 는 있지만 **왜 건너뛰었는지의 개수**가 없다.
   → 이유별로 세어 돌려주고 화면에 적는다(«상한 초과 N · 이미 실행중 M»). 조용한 0 을 만들지 않는다.
2. **상한 12가 지금도 맞나.** 24개를 한 번에 원하는 사용 패턴이라면 순차 재개(배치)로 풀지,
   상한을 올릴지 판단이 필요하다. ⚠️ OOM 커널패닉 전력이 있다(2026-06-19, python 워커 62개).
3. **`--resume` 정규식의 오탐.** `ps` 전체에서 긁으므로 복구표를 띄운 다른 프로세스나 명령줄 잔재가
   걸릴 여지가 있는지 본다.
