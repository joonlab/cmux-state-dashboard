## Era 1 — 탄생과 「충실 복원」 (7/2 ~ 7/13)

### 0번 문장은 발주서가 아니라 사고 신고였다

> **[7/2 18:59]** "지금 cmux 워크스페이스와 탭들 열려있는 거 있잖아. 이거 전에 claude code
> 세션 열려있던 게 다 꺼져버렸는데 그거 복구 가능해?"

진단 결과는 **손실 0**이었다. 대화는 `~/.claude/projects/*.jsonl`에 그대로 있었고,
결정적으로 cmux가 각 탭의 실행 명령에 `claude --resume <세션ID>`를 **이미 저장해 두고 있었다.**
"어느 탭이 어느 세션이었나"의 매핑이 처음부터 디스크에 있었던 것이다.
실측: 워크스페이스 60개 중 52개가 세션과 연결, 고유 세션 49개, `.jsonl` 전부 생존.

복구표를 텍스트 파일로 뽑아 건네자 **8분 뒤** 진짜 발주서가 왔다.

> **[7/2 19:07]** "cmux window, workspace, tab 모두 관리할 수 있는 로컬 웹서버 만들자.
> 모르고 컴퓨터가 꺼지거나 cmux 가 강제종료 되어버리더라도 이전 상태 복구해버릴 수 있도록 하는 그런.
> (…) 로컬 웹서버는 맥북이 껐다 켜지더라도 알아서 살아있으면 좋겠어. pm2 로 관리되고
> tailsacle 서버로 묶여서 `http://joonlab-m5-max:{port_num}` -> 이런 식으로 관리되면 좋겠어."

여기에 요구사항이 전부 들어 있고, 만들어진 것도 정확히 이것이다.
**19:07 발주 → 19:14 설계 → 19:58 완성 → 자정 무렵 8커밋.** 하룻밤에 벌어진 일이다.

### 소켓 접근 전쟁 — 진단이 일곱 번 뒤집혔다

만들자마자 벽에 부딪혔다. pm2로 띄운 대시보드만 cmux 소켓에 못 붙었다.

| # | 가설 | 실측 |
|---|---|---|
| 1 | pm2가 stale한 `CMUX_SOCKET_PATH`를 물려줌 | ❌ `env -i`도 PONG |
| 2 | `__CFBundleIdentifier`로 cmux가 "내부 프로세스"로 오인 | 부분 정답, 근본 아님 |
| 3 | `GHOSTTY_*`·`TERM_PROGRAM` 잔존 | ❌ 최소 env로도 실패 |
| 4 | 프로세스 **조상** 문제 | ❌ pm2 데몬 부모는 launchd(1) |
| 5 | env 문제 | ❌ **pm2가 넘긴 env를 그대로 복사해 내 셸에서 실행 → PONG** |
| 6 | GUI(Aqua) 세션 → `launchctl asuser` | ❌ 여전히 거부 |
| 7 | **`socketControlMode`가 아직 `cmuxOnly`** — 파일엔 `password`라 써 있는데 라이브 `access_mode`가 안 바뀜 | ✅ |

**소켓 모드는 `reload-config`로 안 먹고 앱 시작 시에만 읽힌다.**
그런데 재시작하면 지금 열린 탭이 다 닫히는데, **그건 이 도구가 막으려는 사고 바로 그것이었다.**

> 그래서 정해진 원칙: **핵심(복구·모니터링)은 소켓 없이 파일 기반으로 100% 동작시키고,
> 소켓이 필요한 제어 버튼만 「가능할 때」 동작하도록 우아하게 강등한다.**

이 구조 덕에 이후 cmux가 몇 번이나 소켓을 끊어먹어도 **복구 기능은 한 번도 죽지 않았다.**

> **교훈** — 설정 파일에 쓴 값 ≠ 프로세스가 지금 쓰는 값. 라이브 상태를 직접 물어봐야 한다.

### 첫날 밤에 판정 기준이 두 번 뒤집혔다

23:13, 첫 번째 성격 전환이 왔다.

> **[7/2 23:13]** "복구되는 게 기존 cmux 윈도우, 워크스페이스, 탭에서 그 고정되어있고,
> 워크스페이스 색상이 적용된 상태로 복구되는 게 아니라 **아예 새로운 워크스페이스에서 새로 열리는데**,
> 이 부분 개선하고 최적화해줘."

→ 항목마다 맨 워크스페이스를 만들던 것에서 **워크스페이스 단위 재구성**으로.

23:42, 중복 생성 신고. 원인은 dedup을 "claude가 **실행 중인가**"로만 본 것이었다.
재시작 후엔 탭은 있어도 프로세스가 죽어 있어 감지가 안 됐다.
→ 판정을 "워크스페이스 **제목이 존재하는가**"로 바꿨다.

**6분 뒤 사용자가 이 수정 자체를 반박한다. 이 프로젝트에서 가장 중요한 한 문장이다.**

> **[7/2 23:48]** "복원할 항목이 없다고 하는데 **claude code 세션이 열려있지 않으면 복원이
> 안 된거라고 봐야지.** 현재는 워크스페이스 구조, 탭 구조, cmux browser 정도만 복원되어있는
> 상태에서 이 현재 열려있는 구조를 그대로 반영해서 복원하고 싶은 claude code 세션이 지금 구조에
> 맞게 열리게 하게끔 하는 걸 원하는거야. 만약에 복구하고 싶은 세션을 배정할 워크스페이스와 탭이
> 없다고 하면 그때 새로 만들면 되는 거고."

**"구조는 이미 복원됐지만 그 안의 claude는 안 돌고 있다"** — 이 구분을 사용자가 짚어 줬다.

> **교훈** — 하나의 dedup 축으로 성질이 다른 두 자원을 판정하려 하면 반드시 한쪽이 틀린다.
> 구조는 **존재 여부**로, claude 세션은 **실행 여부**로 나눠야 한다.

### 「600개 서피스 스탬피드」와 두 번째 전환

> **[7/6 15:55]** "지금 cmux 쓰면 막 한번에 많은 게 열리면서 엄청 부하가 많이 걸려서
> **아예 로딩 조차가 안 되고 입력도 못 하는 상황**인데 어떻게 해결해"

진단이 반전이었다 — **cmux 프로세스가 0개고 메모리는 92% 여유였다.**
"실행 중 과부하"가 아니라 **켜는 순간의 복원 스탬피드**였다. 저장된 세션 하나에
브라우저 패널 **434개**를 포함해 서피스 600개 이상이 들어 있었고, 그중 322개가 창 두 개에 몰려 있었다.

그리고 사용자가 세션 파일을 비우기 전에 되물었다 — **자기가 만든 안전망이 정말 안전망인지.**

> **[7/6 16:00]** "이렇게 해도 `http://joonlab-m5-max:7788/` -> 이걸로 관리되고 있는
> cmux 상태 복구하는 로직에는 영향 없는거지?"

대시보드는 세션 파일을 **읽기만 하고 되쓰지 않으며**, 복구 데이터는 자체 DB와 `data/backups/`
원본에서 온다는 걸 코드로 검증했다. 그리고 **비우기 직전의 골든 스냅샷을 동결해 두는 습관**이
여기서 생겼다. 이 한 번의 신중함이 이후 몇 번이나 프로젝트를 구한다.

20분 뒤, 두 번째 성격 전환:

> **[7/6 16:20]** "이게 그냥 단순히 claude code 세션 복원하는 것 뿐만 아니라 **내가 원하는
> cmux 윈도우, 워크스페이스, 탭, 브라우저 레이아웃 이런 게 잘 담겨진 정보가 그대로 남아서
> 내가 선별적으로 바로 복원할 수 있게** UI/UX 적으로 개선해보면 좋겠어."

조사해 보니 **네이티브 세션 JSON 하나에 100% 충실 복원에 필요한 게 이미 다 있었다** —
스플릿 트리(`dividerPosition`/`orientation`), 탭 그룹·선택탭, resume 명령, 브라우저 URL,
워크스페이스 이름·색·고정·cwd, 창 프레임까지. **대시보드가 그 `layout` 트리를 통째로 버리고
서피스만 평탄화해 저장하고 있었을 뿐이다.**

3-Phase로 갈아엎었다 — 캡처(`layout.py`) / 복원(`restore.py`) / 미니맵 UI.
큰 발견 하나: **`new-workspace --layout`이 스플릿을 네이티브로 지원한다.** 명령형 조합 없이
워크스페이스 하나를 **단일 호출로 통째 재현**할 수 있었다.

### 성공한 API, 보이지 않는 결과

> **[7/6 17:19]** "이렇게 해서 상태복원 시도했는데 **cmux 에서 아예 안 열려**"

로그를 보니 복원은 **성공**이었다. 200 OK, 창·워크스페이스·3페인 스플릿까지 실제로 생성돼 있었다.
그런데 화면엔 아무것도 없었다. 원인은 **모든 서피스가 `in_window=false`** —
`focus=false`로 백그라운드 창에 만들면 cmux는 서피스를 창에 **부착(realize)하지 않는다.**
정의만 되고 그려지지 않는다.

> **교훈** — cmux에서 "만들었다"와 "떠 있다"는 다른 사건이다. 200 OK와 사용자 화면 사이에
> `in_window`라는 층이 하나 더 있다.

### 만들 수는 있어도 지울 수는 없는 도구

검증을 라이브 cmux에서 반복하다 테스트 창이 **12개**까지 쌓였는데 지울 수가 없었다.
`close-workspace`는 창의 마지막 워크스페이스를 못 닫고, `close-window`는 pm2/asuser
컨텍스트에서 **아예 안 먹는다**(cmux가 GUI 비연결 caller의 파괴적 창 조작을 거부).

이 비대칭은 7/24의 「임시 저장 후 원래 것 끄기」 요구로 되돌아온다.

### 두 세대의 코드가 겹쳤다 — 이중 주입

> **[7/12 21:06]** "근데 자꾸 복원하면서 claude code 입력창에 이렇게 명령어가 입력되어있는
> 상태로 복원되더라고."

처음엔 "복원이 안 된다"로 읽고 엉뚱한 곳을 파기 시작했는데, 사용자가 **진단을 교정했다.**

> **[7/12 21:14]** "아냐 **잘 복원은 됐는데** 복원되고나서 claude code 입력창에 명령어가
> **또** 입력되어있다는 말이었어"

이 한 줄로 방향이 즉시 좁혀졌다. 같은 명령이 두 경로로 중복 적용되고 있었다 —
7/6에 만든 **surface `command`**(셸에서 실행 → claude 정상 기동)와
7/2에 만든 **`run_in_surface`**(그 직후 `send_text+Enter`로 이미 떠 있는 claude 입력창에 또 타이핑).

> **교훈** — 기능을 새로 만들 때, **그 일을 이미 하고 있던 옛 경로를 지웠는지** 확인하라.
> 두 경로 모두 "잘 돌고" 있었기 때문에 로그로는 안 보였다. 증상은 오직 화면에만 있었다.

### 재현 여섯 번이 전부 깨끗하면 코드가 아니라 「경로」를 의심하라

> **[7/13 06:40]** "지금 해보려니까 또 그러네."

여섯 가지 방식으로 재현을 시도했고 **전부 깨끗했다.** 결정적 단서는
**pm2 로그에 사용자의 복원 API 호출 흔적이 아예 없었다**는 것 — 그 "복원"은 대시보드를 안 거쳤다.

추측으로 코드를 더 고치는 대신 **미해결로 남기고 조사를 멈췄다.**

> "여기부터는 추측이 아니라 사용자의 실제 조작을 알아야 정확히 고칩니다."

### 「왜 좋아졌지?」는 「왜 나빠졌지?」만큼 중요하다

> **[7/13 06:54]** "지금 확인해보니까 여기가 소켓제어 활성화라고 나오는데 **내가 아까
> 물어봤을 당시에는 비활성화라고 떴었어. 갑자기 왜 활성화 된거지?**"

이 질문이 진짜 문제를 드러냈다. 활성화된 이유는 디버깅 중 `self_heal_password()`를
**수동으로 한 번 돌린 것**이었고, 그 뒤에 있던 진짜 문제는 **cmux가 `socketPassword`를
반복적으로 지운다**는 것이었다(비번을 파일로만 넣으면 cmux가 자기 설정을 저장할 때 덮어씀).
그런데 self-heal은 **기동 시에만** 돌고 있었다.

→ health 폴링마다 self-heal. 비번을 일부러 지워도 폴링 1~2회면 회복한다.

## Era 2 — 그룹·스냅샷·렉 (7/16 ~ 7/28)

### 설정 스위치가 보인다고 그게 모든 경로를 덮지 않는다

> **[7/16]** "복구하고 나서 workspace 새로 열면 항상 이렇게 돼" (남의 프로젝트 폴더에서 시작)

`app.workspaceInheritWorkingDirectory: false`로 고쳤다. 그런데 30분 뒤:

> **[7/16 23:59]** "새로운 workspace 열면 괜찮은데 **같은 group 에서 workspace 를 새로 열면**
> 또 그 group 의 캐시? 공유되는? 그 폴더에서 열리는듯 이것도 해결해"

그룹의 `+` 버튼은 그 설정을 **완전히 우회한다.** cmux 소스를 읽어야 확정됐다 —
`WorkspaceGroupCoordinator.swift`가 앵커의 cwd를 **명시 인자로 넘기며** 상속 플래그를
무력화하고 있었다. 끄는 설정이 없고, 유일한 레버는 **앵커의 cwd 자체**였다.

> **교훈** — 스키마·문서에 다 없으면 **소스가 정본**이다.
> "설정이 있다"와 "그 설정이 이 경로를 덮는다"는 별개 명제.

### 복구 장치를 실패할 수 있는 전제 뒤에 두지 마라

> **[7/18]** "이게 claude code 세션 resume 할 때 **작업 폴더 옮긴 걸 인지하지 못 하더라고.**
> `cd: no such file or directory`"

cmux는 resume 바인딩을 저장할 때 런치 폴더가 아니라 **저장 순간 터미널이 drift해 있던 폴더**를
`cd '<경로>' &&`로 박는다. 그 폴더가 rename되자 `cd`가 실패하고 `&&`가 단락되면서 —
**바로 그 drift를 고치려고 만들어 둔 wrapper가 실행조차 안 됐다.**

→ `resolve_launch_cwd()`(세션 `.jsonl`의 프로젝트 폴더 인코딩에서 진짜 launch cwd 복원) +
`&&`(fatal)를 **`2>/dev/null;`(non-fatal)**로 교체.

### 탭 319개 — 앱 버그인가 데이터 볼륨인가

> **[7/24 02:18]** "지금 cmux 가 **굉장히 렉이 많이 걸리고 있는데**, 원인 면밀히 파악해"

서피스 335개 중 **브라우저 탭이 319개**였고, 그중 296개(88%)가 **워크스페이스 하나**에 몰려 있었다
— cmux browser로 조사하며 연 탭이 하나도 안 닫힌 것.

스택 샘플 2,094개를 분해하니 `NSView _layoutSubtreeWithOldSize:` 재귀가 **44단계**.
거기에 같은 워크스페이스의 claude 스피너가 **초당 ~10회 탭 제목을 갱신**해 매번 레이아웃을
무효화하고 있었다. **"탭 319개 × 제목 갱신"의 곱**이 렉의 실체다.

정리 후 **CPU 100~105% → 2.6~11%**, 서피스 335 → 39.

같은 증상에 기존 문서가 "앱 업데이트"를 처방하고 있었고 현재 버전이 이미 그 버전이었다.
감별은 스택 시그니처로 했다 — SwiftUI `LazySubviewPlacements`면 앱 버그, AppKit
`_layoutSubtreeWithOldSize` 44단계면 데이터 볼륨.

> **교훈** — CPU 100%를 만나면 앱 버그로 오귀인해 재시작하지 말고 **탭 수부터 세라.**
> 재시작해도 탭이 남아 재발한다.

곧바로 사용자가 **도구가 아니라 에이전트의 사전 지식까지** 고치자고 했다:

> **[7/24 02:37]** "cmux browser 켤 때 50개 넘어가면 오래된 것부터 순차적으로 끄도록 하는 거 가능?
> **hook으로 해두면 좋을 것 같아. CLAUDE.md 에도** cmux browser 다룰 때 그런 거 미리 인지하고

→ PostToolUse 훅(워크스페이스별 50 / 전역 150, 오래된 순, 터미널·포커스 탭 보호, 닫은 탭 URL 로깅)
**+ 규칙 문서**. 사후 안전망과 사전 인지의 2단 구성이 여기서 나왔다.

### 워크스페이스 3개가 조용히 사라졌고, 복구가 2차 사고를 냈다

빈 워크스페이스 하나만 닫으려 했는데 다른 창이 14 → 11이 됐다. 색상 스크립트 실행 시점에
이미 줄어 있었으므로 **닫기 명령 이전에 사라진 것**이다. 원인을 단정하지 않고
**추가 파괴 작업을 즉시 중단**했다.

그런데 복구하려고 실행한 `cmux restore-session`이 저장 스냅샷 **전체**를 새 창 두 개로 열어,

(보호창의 워크스페이스 목록을 스냅샷해 두고 **매 파괴 명령 후 대조**, 하나라도 잃으면 중단)를
걸고 하나씩. 15개 제거, 보호창 손실 0.

> **교훈 둘** — ① 손실을 발견하면 **원인을 단정하기 전에 파괴 작업부터 멈춘다.**

### 사용자가 보는 화면이 판정 기준이다

이름·설명 드리프트를 전수조사하다 한 워크스페이스를 "애매하다"고 보고했더니:

> **[7/27 08:35]** "라고 하는데 그게 무슨 말이야.. **나한텐 이렇게 잘 보이는데?**"

워크스페이스에는 제목/설명 필드가 셋이다 — ① 이름 ② 설명 ③ **터미널 탭 제목**.
①②는 사이드바에 보이고 ③은 안 보인다. ③은 그 세션에서 예전에 잠깐 한 서브작업의 **잔상**인데,
그걸 현재 작업 신호로 같이 본 게 오탐의 원인이었다.

> **교훈** — 드리프트 판정의 진실 원천은 **사이드바 표시값**. 탭 제목은 보조 신호.

### 세션이 tmux 역할을 대신하고 있었다

에이전틱 개발환경 3층 모델(워크스페이스/터미널/프로세스 수명)을 자기 환경에 실측 대입한 결과,
**글을 그대로 이식하면 안 된다**는 결론이 나왔다.

- Layer 3(프로세스 수명)는 이미 채워져 있었다 — tmux가 아니라 pm2 13앱 + launchd로.
- Layer 1의 "task identity"가 **구조적으로 성립하지 않았다** — 세션의 **98%가 `~`에서 실행**되므로
  `pwd`/`git branch` preflight가 아무것도 알려주지 않는다.
  **워크스페이스의 이름·설명·색이 유일한 task identity**였고, 그래서 그 라벨을 최신으로 유지하는
  도구가 필요했다.
- 진짜 문제는 글이 다루지 않은 자리에 있었다 — **claude 세션이 tmux 역할을 대신하고 있었다.**
  10일간 대화 없는 세션이 384MB를 물고 살아 있는 건 "장기 프로세스 유지"가 아니라
  **닫는 규칙이 없어서** 생긴 잔여물이었다.

→ `claude-session-reaper.py`(판정 신호 = 제어 터미널 mtime). **세션 26개 → 11개, 16.2GB → 8.4GB.**
프로세스만 죽이고 **워크스페이스·레이아웃·색은 보존**한다 — 워크스페이스를 "실행 중인 프로세스"가
아니라 **자리(place)**로 다루는 관점이고, 관제실 전체의 설계 철학과 맞닿는다.
그 판정기를 그대로 import해 **「세션 건강도」 탭**이 생겼다(종료 버튼은 일부러 두지 않았다).

## Era 3 — 유실 사고와 「지금 어디」 (8/4 ~ 8/26)

### ★창 하나가 통째로 사라졌다 — 이 프로젝트 최대의 사고

> **[8/4 22:49]** "분명 15분 전에 window 3개 띄워서 쓰고 있었는데 재부팅 되면서 다 날라가서

대시보드 버그로 보였지만 아니었다. 같은 스냅샷 안에서 두 소스가 갈렸다.

| 소스 | 창 수 |
|---|---|
| 소켓 `tree` (라이브) | **4** |
| native JSON (복원 원천) | **2** |

백업 파일 14개를 직접 세어도 전부 2개. **cmux가 그 창의 존재를 세션 JSON에 아예 안 쓰고 있었다.**

사슬을 재구성하니 — **8/3 22:52:38**에 창 하나(맥북 내장 화면)가 native 저장에서 이탈했고
(`ws 51→48`, `claude 44→41`로 정확히 그만큼 감소), 이후 **하루 종일** 그 창에서 워크스페이스를
9개까지 늘렸지만 native엔 **한 줄도** 기록되지 않았다. 8/4 재부팅으로 통째 소실.
cmux 자신의 `closed-item-history`에도 없었다 — **닫힌 게 아니라 존재를 몰랐던 것이다.**

그리고 백업이 정확히 **60개(상한)**라 마지막 온전본이 곧 밀려날 상태였다. 급히 대피시켰다.

**핵심은 여기다.** 대시보드가 창 수를 native 기준으로 표시한 건 7/23에 "복원 원천에 맞춘다"고
통일한 결과였다. **정본을 정한 것 자체는 옳았다.** 틀린 건 어긋났는데도 경고가 없었다는 점이다.

> **★교훈 — 두 소스가 갈리면 한쪽을 정본으로 삼되, 불일치는 반드시 드러내라.
> 조용히 한쪽을 고르면 유실도 조용히 일어난다.**

수정의 핵심은 **삽입 지점**이었다. `restore.load_layout_windows()`는 **복구 뷰와 실제 복원이
공유하는 단일 지점**이라, 여기서 tree-only 창을 합성하면 **과거 스냅샷 전부에 소급 적용**된다.
(memoize **이후**에 붙여 근사값이 DB 복원 원천을 오염시키지 않게 했다.)

실증: 문제의 스냅샷이 `창2·ws31·claude22` → **`창4·ws41·claude28`.**
워크스페이스 9개·브라우저 탭 43개가 복원 대상으로 부활했다.
한계도 배너에 명시했다 — 근사 복원이라 **분할 비율/방향·색·그룹은 복원되지 않는다.**

### "대조 불가"와 "대조 실패"는 다르다

과거 스냅샷 카운트를 고치는 백필을 **세 번** 돌려야 했다.

- **1차** 뒤에 같은 창이 **네이티브 6 + 합성 6으로 이중 계상**된 걸 발견했다. 원인은
  **구 cmux(0.64.17 이전) 세션 JSON엔 `workspaceId` 필드가 아예 없다**는 것.
  UUID 집합이 **비는 경우**를 "대조 불가"가 아니라 "전부 불일치"로 처리해 모든 창을
  tree-only로 오판했다. 그대로 복원했다면 워크스페이스가 두 배로 생겼을 것이다.
- **2차** 뒤에도 값이 틀렸다. 스킵 로직이 *"저장된 레이아웃이 있고 tree-only가 없으면 안 바뀐다"*고
  가정했는데, **1차 백필이 이미 DB를 오염시켜 그 가정이 깨져 있었다.**
- **3차** — 스킵 전에 **저장값과 계산값을 실제로 대조.** 611건 추가 교정 후 전수 dry-run 갱신 0.

> **교훈** — 갱신 스킵 판정은 "바뀔 리 없다"는 **추론**이 아니라 **저장값 대조**로.
> 앞선 실행이 남긴 오염은 그 추론의 전제를 무너뜨린다.

### "안 보인다"는 신고에 UI부터 고치지 마라

### ★「지금 어디」의 탄생 — 두 번째 성격 전환

### 성공 문구가 거짓말을 하면 안 된다

> **[8/22 12:47]** "이렇게 이동이라고 하면 그걸로 focus 가 이동되어야 하는데 **그냥 이동했다고만
> 떠서 내가 직접 cmux window 를 찾아야하는데..**"

`surface.focus`는 **cmux 내부에서만** 바꾼다. 브라우저에서 대시보드를 보고 있으면 cmux는 뒤에 남는다.
**탭은 이미 이동했는데 화면은 그대로**였다. → `open -a`로 앱 최전면화까지.

여기서 원칙 하나가 굳었다 — **전환 실패를 삼키지 않는다.** 응답의 `activated`가 false면
토스트가 `"탭은 이동함 · cmux 앱 전환 실패"`로 뜬다. *"성공 문구만 띄우면 이번과 똑같이 또 헤매게 되니까요."*

### ★mtime 오판 — "16초 전"이 실은 23.8시간 전

> **[8/22 13:04]** "잘 되긴 하는데 이런 건 **방금 전 claude code 열어서 한 것도 아닌데
> 왜 몇 초 전에 활성화되었던 걸로 나오지?**"

활동 시각을 `.jsonl` 파일 mtime으로 잡은 게 원인이었다.
**실행 중인 세션은 대화가 없어도 파일이 계속 touch된다.**

| | mtime − 마지막 대화 괴리 |
|---|---|
| 실행 중 세션 45개 | 중앙값 **1494분**, 89%가 10분 초과 |
| 종료된 세션 2055개 | 중앙값 **0.3분** |

→ `lastActivity = max(마지막 user/assistant 발화, cmux 알림)`. 폴백을 쓸 때는
`activitySource`에 **"파일시각(부정확)"이라고 드러낸다.** transcript 캐시 키도 mtime → **size**로
(append-only 로그라 **크기가 곧 버전**이고 touch로는 안 바뀐다).

결과: **입력 대기 25 → 8, 유휴 19 → 36.** 문제의 탭은 23.8시간 전 유휴로 정정됐다.

정확한 writer는 끝내 특정하지 못했다. 후보를 실험으로 배제해 나가다 멈췄고, 그 판단 기준을 이렇게 적었다:
> **"조치는 원인과 무관하게 성립해서 여기서 멈췄습니다."**

### ★★sticky 헤더가 클릭을 가로챘다 — 자동 테스트가 못 잡은 것

> **[8/24 03:02]** "이런 문제 발생중. 근데 여기에 있는 **포커스 버튼 누르면 잘 이동되는 걸 보면
> 기능상 문제는 없어보이는데..**"

다섯 가지 가설을 자동화로 **전부 배제**했다 — 서버 상태 동일, surface UUID 정상, 유휴 카드도
클릭 이동 성공, 다른 창도 실제 최전면(`screencapture`로 확인), 좌표도 안 밀림.
**재현이 안 됐다.**

판을 뒤집은 건 **사용자에게 증상을 물은 것**이었다. "클릭했을 때 정확히 어떤 일이 일어나나요?"를
네 갈래로 나눠 물었고, 답은 **"아무 반응 없음"**이었다. 아무 반응도 없다면 화면 전환 문제가 아니라
**클릭 자체가 안 나간 것**이다.

```
document.elementFromPoint(카드중앙)  →  <label class="toggle">   ← sticky 헤더 안의 토글
```

헤더 **89px**, 카드 평균 높이 **110px**. 스크롤을 내려야 보이는 카드에서만 생기니
"위는 되고 아래는 안 된다"와 정확히 맞는다.

> **★교훈** — *"`cmux browser click`은 **셀렉터로 요소를 직접 클릭해서 좌표·가림과 무관합니다.
> 사람의 마우스와 경로가 달라서**, 제가 '정상 동작한다'고 여러 번 확인한 게 실제 클릭을
> 검증한 게 아니었습니다."*
>
> 셀렉터 클릭은 **「요소가 존재하는가」**를 검증하고, 사람의 클릭은
> **「그 지점이 이 요소에 도달하는가」**를 검증한다. 가림·z-index·sticky·overlay는
> 전자를 통과하고 후자에서만 걸린다. → 클릭 검증 기준을 `elementFromPoint` 도달 여부로 바꿨다.

같은 조사에서 **고친 게 반영되지 않고 있었다**는 것도 드러났다(서버 CSS 32규칙 vs 페이지 30규칙).
`Cache-Control: no-store`를 붙여도 WKWebView는 캐시본을 계속 썼다.
→ HTML 서빙 시 자산 URL에 **파일 mtime 버전**을 주입.

### 틀린 값을 채우면 사용자가 그걸 근거로 잘못 판단한다

> **[8/25 08:48]** "이걸로 탭을 열려고 하니까 얘가 뜨네? 이게 되어야 하는데.."
> (제목이 같은 탭 둘 중 엉뚱한 쪽이 열렸다)

원인이 둘이었다.

① **찾던 탭이 목록에 아예 없었다.** claude 프로세스를 `--session-id`/`--resume` **인자가 붙은
것만** 수집했는데, 그 인자는 **cmux가 기존 세션을 이어받을 때만** 붙는다. 새로 시작한 세션엔 없다.
**카드는 옳았고, 목록이 불완전했다.** → 판별을 인자가 아니라 **부모 프로세스** 기준으로.

② **'현재' 탭이 제목 추측으로 허상을 만들었다.** 사용자가 "저 창이 맞다"고 판단한 근거 화면이
바로 그것인데, 제목이 같은 워크스페이스가 둘이면 한 세션이 양쪽에 붙는다.
→ `CMUX_PANEL_ID` 정확 매핑을 1순위로, 제목 추측은 확정 세션 재사용 금지,
**둘 다 없으면 그냥 비운다.**

> **교훈** — *"둘 다 없으면 그냥 비웁니다 — **틀린 값을 채우면 사용자가 그걸 근거로
> 잘못 판단한다**는 게 이번 사고가 보여준 것이라서요."*

### 원인을 못 잡았으면 단정하지 않고 다음을 위한 로그를 심는다

유령 경고(`탭을 못 찾아 목록에서 제외한 claude 1개`)가 계속 떴는데 **pid가 매번 바뀌었다.**
유력 원인은 프로세스 목록 8초 캐시와 매번 읽는 트리의 시차인데, 25회 반복 관측에서 **0건**일 만큼
드물어 발생 순간을 못 잡았다.

> *"그래서 '이것이 원인이다'라고 **단정하지는 않겠습니다.**"*

→ 경고 직전 `os.kill(pid, 0)`로 생존 확인. 죽었으면 유령이므로 조용히 버리고,
살아 있는데 탭이 없으면 **경고 유지 + 진단 정보를 서버 로그에** 남긴다.

### 칸반 보드 — 목록은 "무엇이 있나"를 답하지만 "어디에 있나"를 못 답한다

> **[8/25 22:57]** "현재 cmux window, group, workspace, tab 은 너무 직관적으로 보기가 힘들어
> **윈도우를 다 한번에 띄워두고 보기도 어렵고.** (…) 지금은 그냥 쭉 위에서부터 박스가
> 나열되어있지만, 이걸 좀 더 직관적으로 깔끔한 레이아웃으로 **바로 아 이게 여기 있구나
> 이게 이 윈도우가 이 그룹 안에 이게 속해있구나** (…) **어떤 상태구나** 등을 알 수 있도록 해보자."

창을 다 띄워 볼 수 없다는 물리적 제약이 그대로 화면 구조 요구가 됐다 — **컬럼 하나 = 창 하나.**
4탭 전부를 같은 레이아웃으로 통일했다(한 번 익히면 네 화면에서 통한다).

다만 **'복구' 탭만 압축하지 않았다** — *"분할 배치를 눈으로 보고 고르는 게 이 탭의 핵심"*이라서.
일관성보다 그 화면의 목적이 우선이었다.

**데이터가 설계를 가른 지점**도 있다. 워크스페이스 50개 중 claude 탭이 2개 이상인 곳은 **2개뿐**이라
*"항상 2단으로 만들면 대부분 불필요한 중첩"*이 된다. → **탭 2개 이상일 때만** 묶는다.

**창 순서를 활동순으로 하지 않은 이유**도 명시적으로 남았다 — *"방금 움직인 창이 앞쪽으로 몰립니다.
순서가 계속 바뀌어 찾던 창이 이동합니다."* → 활성 창만 앞, 나머지는 번호순.
**위치가 예측 가능해야 눈이 익는다.** 컬럼 **안에서만** 최근 활동순.

### 폴링이 화면을 되돌리고 있었다

> **[8/26 01:43]** (스크롤이 원점으로 튀는 문제) "그리고 두번째로는 **그룹 정보가 칸반보드에는 없어.**"

5초/8초 폴링마다 `innerHTML`을 통째로 갈아치우고 있었다. 가로 스크롤이 0으로 튀고 펼쳐둔 카드도
같이 접혔다. → **내용이 같으면 DOM을 아예 건드리지 않는다.** 바꿔야 할 때만 스크롤·펼침을 복원하되,
**복원 키는 재렌더에도 안 변하는 UUID**로(순번 id는 매번 바뀌어 못 쓴다).

그룹 누락은 데이터 경로 문제였다 — **cmux는 워크스페이스 그룹을 라이브 트리에 실어주지 않는다.**
네이티브 세션 파일에만 있다.

### 폴링 화면에서 API 응답이 캐시되면 최악이다

검증 중 더 위험한 걸 발견했다 — 브라우저의 `assetVersion`이 **006**인데 서버는 **031**을 주고 있었다.
**`/api/nav` 응답 자체가 캐시**되고 있었다(정적 파일엔 no-store를 붙였는데 API엔 안 붙였다).

> *"폴링 화면에서 응답이 캐시되면 **'갱신되는 것처럼 보이는데 값이 안 바뀌는'** 최악의 상태가 됩니다."*

→ `/api/*` 전체 no-store + **새 버전 알림 배너**(자동 리로드는 하지 않는다 — *"복구 탭에서
선택 중일 수 있어서요."*)

## Era 4 — 보드·편집 모드·디자인 시스템 (8/25 ~ 8/31)

### ★세 번째 성격 전환 — 읽기 전용에서 제어면으로

> **[8/26 03:05]** 칸반 보드에 드래그앤드롭 편집 모드를 추가한다.
> - **실제 cmux에 반영**
> - 헤더의 "편집" 버튼으로 진입, **편집 중엔 폴링 정지**
> - **되돌리기(직전 배치 복원) 먼저 설계할 것**

세 줄이 이 전환의 성격을 다 말한다. ① 화면만 바꾸는 게 아니다. ② 읽기와 쓰기가 같은 화면에서
싸운다는 걸 이미 알고 있다. ③ **기능보다 취소를 먼저 요구했다.**

되돌리기는 별도 경로가 아니라 **적용과 같은 엔드포인트·같은 payload 모양**으로 만들어졌다.
근거: *"복원 전용 경로를 두면 그쪽만 덜 검증된 채 남으므로."*

조작 대상이 된 순간 cmux는 순순히 따르지 않았다 — [cmux 실측 노트](CMUX-NOTES.md)의
「조용한 거짓말」 절이 그 대가다.

그리고 **pin/unpin을 범용 통로로 만들지 않았다.** 같은 `workspace-action`에
`close-others`·`close-above`·`close-below`가 들어 있어서 — *"액션 이름을 화면에서 받는 순간
워크스페이스를 무더기로 닫는 길이 열린다."* 토글이 아니라 **원하는 최종 상태**를 받는 것도
같은 계열의 방어다(화면 상태가 낡으면 토글은 정확히 반대로 뒤집힌다).

### 검증이 무효였다 — dispatchEvent는 히트테스트를 건너뛴다

> "이 탭의 어느 부분을 클릭해도 확장되게 해줘. 지금은 어떤 부분은 클릭이 되고 어떤 부분은
> 클릭이 안 되는데.. **UX가 너무 안 좋은듯**"

고치고 "전부 통과"라고 보고했는데 사용자가 **"이 부분은 아예 클릭 안 되는듯?"**으로 되돌아왔다.
원인은 코드가 아니라 **검증 방법**이었다 — `dispatchEvent`로 요소에 직접 쏘면 가림을 통과한다.
(8/24 sticky 헤더 때와 **같은 함정에 다시 걸린 것이다.**)

실좌표 + `elementFromPoint` + `mousedown→mouseup→click`으로 다시 재니
**진짜 재현 가능한 결함**이 나왔다 — 누르며 **2~3px만 끌려도** 글자가 선택되고 그 클릭이 조용히
무시됐다. → 압축 행에 `user-select:none`. *"버튼처럼 눌리는 자리이지 읽어서 복사하는 자리가 아니다."*

### 세션은 사람이 안 건드려도 움직인다

> **[8/26]** "나 이것들은 **방금 보지도 않고 아무것도 안 했는데 왜 9분, 10분으로 뜨는거야.**"

transcript를 보니 최근 두 줄이 **백그라운드 알림**이었다(`promptSource=system`).
`lastMessageAt`이 `type in (user, assistant)`만 세어 그게 그대로 "최근 활동"이 됐다.
실측 54개 중 **8개**가 시스템 발.

→ 정렬은 안 건드리고 **`🤖 자동` 배지 + `lastHumanAt`**을 함께 표시.

그리고 이 세션에서 사용자의 한 줄이 작업 방식을 굳혔다:
> **"어떻게 조치할지 애매하면 askuserquestion 툴로 물어보고 진행해"**

### 한도가 안전장치가 아니라 장애 원인이었다

> **[8/28]** "간헐적으로 이런 화면이 뜨더라고. 아예 안 뜨게 할 수 없나.. **유독 오늘따라 많이 그래.**"

화면에 뜬 `rc=-2`는 **증상이지 원인이 아니었다** — 음수 rc는 "시그널로 죽었다"는 뜻이고,
범인은 pm2였다.

```
16:48:51  재시작=72  RSS=278MB  가동=16s
16:49:13  재시작=73  RSS=280MB  가동= 6s
16:49:43  재시작=74  RSS=272MB  가동= 8s
```

앱이 **30초마다 재시작**되고 있었다. RSS가 `max_memory_restart`(150MB)를 넘겨 pm2가 SIGINT를
보내면 진행 중이던 cmux 자식도 같이 죽어 `rc=-2`가 되고, 트리를 못 읽으면 모든 탭이 '위치 불명'이
되어 목록에서 통째로 빠진다.

메모리를 단계별로 재니 **`transcript_info`가 +191MB**였다. 꼬리를 통째로 읽고 못 찾으면 4배로 키워
**처음부터 다시** 읽는 구조라 200KB→800KB→3.2MB→8MB를 네 번 읽으며 매번 수만 개짜리 문자열
리스트를 만들었다. 세션이 62개라 고점이 겹쳤다. **"오늘따라 유독"의 직접 원인은 직전 커밋**이었다 —
`lastHumanAt`을 넣으면서 이 경로를 더 자주 끝까지 가게 만들었다.

→ 역방향 256KB 청크 스캔(+191MB → **+18MB**), 트리 조회 실패 시 마지막 성공 트리 재사용,
한도 150M → **512M**(실측 피크 145MB의 3.5배).

> *"`max_memory_restart`는 **누수 백스톱**이지 정상 피크를 조이는 장치가 아니다.
> 정상 동작을 죽이는 한도는 가용성만 깎는다."*

후일담이 인상적이다 — 한도를 올린 뒤 최대치가 **111MB로 내려갔다.**
앞선 측정은 이미 한도 근처에서 GC/재시작 압박을 받던 프로세스였던 것이다.

### 패널 이름을 바꾸면 cmux가 상태 마커를 끊는다

> **[8/31]** "이렇게 **상태를 알 수 없는 것들**도 있던데 원인 파악하고 앞으로 상태 파악할 수
> 있게끔 조치 가능한지 확인해봐"

네이티브 JSON에 결정적 증거가 있었다.

| | 정상 탭 | 끊긴 탭 |
|---|---|---|
| `panels[].title` | `"◑ mlxserve 분석 및 활용 방안"` | `"증명사진 복원"` (마커 없음) |
| `customTitleSource` | — | **`"user"`** |

**패널 제목을 사람이 직접 바꾸면 cmux가 `title`을 그 문자열로 덮어쓰고 그 뒤로 상태 마커를
다시 안 붙인다.** 워크스페이스 이름만 바꾼 건 무해하다(마커는 *패널* 제목에 붙는다).
실측: 78개 중 6개가 이 상태였고, `customTitleSource == "user"`인 패널도 **정확히 그 6개** — 1:1 대응.

→ 마커도 알림도 없을 때만 발동하는 보조 신호(대화 기록의 마지막 레코드 종류로 턴 상태를 되짚음).
**검증이 볼 만하다** — 추정을 새로 넣을 때 기존 정본과 맞춰야 하므로 **마커가 살아 있는 72개로
교차검증**했다. 정확도 71/72(98.6%), **오탐 0건**, 판정 불가 4 → 0.

**일부러 안 한 것도 둘** 있다. ① 마커와 엇갈리는 사례에서 **살아 있는 신호를 추정으로 덮지 않았다.**
② CPU를 신호로 안 썼다 — macOS `ps %cpu`는 **생애 평균**이라 순간 상태가 아니다.

### 접근성 배려가 기능을 죽였다

```css
@media (prefers-reduced-motion:reduce){ .lic.spin{animation:none} }
```

이 맥은 「동작 줄이기」가 켜져 있다. 실측 `animationName: none` — **스피너는 한 번도 돈 적이 없었다.**

> *"그 설정의 취지는 큰 화면 전환·패럴랙스를 줄이라는 것이지 **13px짜리 진행 표시를 없애라는 게
> 아니다.**"* → 끄지 않고 늦췄다(1.1s → 2.6s).

파고들다 함정 하나 더 — `<svg>`의 UA 기본값은 `display:inline`인데 **인라인 요소에는 transform이
안 먹는다.** 애니메이션은 등록되고 `playState`도 `running`인데 화면엔 단위행렬만 나오는 종류다.

그리고 **끝내 눈으로 확인하지 못했다** — cmux browser 서피스가 백그라운드 pane이라 프레임을
안 그린다. 그래서 설계를 바꿨다: **작업중은 움직임 없이도 읽히게**(초록 아이콘 + 초록 선 + 위쪽 배치).
*"회전은 덤이지 유일한 단서가 아니다."*

### 디자인 시스템 — 브랜드층과 의미층을 가른다

> **[8/30]** "일단 UI/UX 개선 작업이 진행될거야. 일단 디자인, 색상 체계부터. 그리고 이모티콘류보다는
> lucid icon 을 사용하게 한다든지. 라이트/다크 모드 토글. 그리고 Cmux 상태 복구 대시보드로 처음엔
> 시작을 했는데 **지금은 cmux 관리툴 자체가 되어버려서 네이밍을 다시 해야할 것 같고**"

개명의 근거를 사용자가 스스로 말했다.

| 결정 | 왜 |
|---|---|
| 색 정의를 `tokens.css` **한 곳으로** | 토큰이 세 곳에 흩어져 있었고 하드코딩 hex 49개·rgba 52개. 같은 뜻인데 값이 달랐던 것도 잡혔다(`#39414f` vs `#3a4250`) — **눈으로는 못 잡는 종류** |

`#3cc492`(대비 4.35) 채택. 더 밝은 후보는 *"AA는 넘지만 민트로 떠서 '누아'가 아니게 됐다."*

**AA 미달 2건은 임의로 고치지 않았다** — 그건 "유휴 카드는 덜 중요하게"의 **의도된 결과**라서,
*"임의로 바꾸면 그 신호가 죽는다."* 라이트를 다크 수준까지 맞추는 데서 멈추고 사용자 결정으로 남겼다.

### 문법 검사는 문법만 본다

훅 단위로 커밋을 쪼개다 `git diff -U0` + `git apply --cached`를 썼는데 **문맥 없는 패치는
부분 적용 시 줄 번호가 어긋나** 파일이 깨졌다. 방식을 바꾼 뒤에도 **깨진 커밋을 하나 만들었다** —
커밋된 nav.js가 선언되지 않은 식별자를 참조하고 있었다.

> **`node --check`는 문법만 봐서 통과시켰다.**

되감아 다시 만들고 **"선언은 사라졌는데 참조가 남은 식별자"를 잡는 검사기**를 추가했다.
그 검사기를 **깨진 커밋에 먼저 돌려 실제로 잡아내는지 확인한 뒤** 적용했다.

## Era 5 — 「막힘」의 발명과 메뉴바 (9/1 ~ 9/7)

### 개념은 세 번의 발화로 좁혀졌다

**① 씨앗 — 우선순위 요구 (8/31)**

> "이거 돌아가고 있는 아이콘은 좀 동적으로 돌아가는 그런 게 들어가면 좋겠는데.
> 그리고 **돌아가는 것보다 자물쇠 아이콘으로 걸리는 상태**, 즉 뭐 물어보는 거나 권한 허용이
> 필요한 게 항상 최상단 맨 왼쪽(앞쪽)에 뜨도록 우선순위를 설정해줘.
> **즉, UX를 생각해서 cmux 를 사용하는 입장에서 뭘 가장 보고 싶어할까를 생각해**"

이때까지 `running`이 최우선이었다. 이 요구로 순서가 뒤집혔다.
`nav.py`에 근거가 남아 있다 — *"'돌고 있는 것'과 '나 때문에 멈춘 것' 중 뒤엣것이 더 급하다 —
**전자는 기다리면 되고 후자는 기다려도 안 된다.**"*

**② 확장 — "권한만이 아니다" (9/2)**

에이전트가 "이 세션은 `bypassPermissions`라 애초에 권한을 물을 수 없습니다"라고 판정하자
사용자가 그 자리에서 잘랐다.

> "**이건 아니야** — 중간에 askuserquestion 으로 물어보거나 hook 으로 무조건 허용 yes/no 를
> 선택하게끔 하는 경우가 있어. **이런 경우엔 권한 자물쇠 표시가 나타나야 해**"

판정 기준은 *권한 모드*가 아니라 **사람이 답해야만 풀리는가**다. 실측이 뒤따랐다 —
알림 1,004건을 재분류하니:

| `subtitle='Waiting'` 알림 | 건수 | 실제 |
|---|---|---|
| `body == "Claude is waiting for your input"` (고정 문구) | 252 | 그냥 프롬프트 대기 |
| 그 밖 (질문 본문이 실림, **180/180 전부 `[선택지]` 포함**) | **180** | **사람을 기다리며 막힘** |

**그동안 이 180번의 「막힘」이 평범한 「대기」로 보이고 있었다.**

**③ 명명 (9/2)** — `question`을 `permission`과 **같은 층·같은 자물쇠**로 올리고,
헤더는 둘을 합쳐 **「막힘 N」 한 칸**으로. *"내가 할 행동이 둘 다 「가서 답한다」로 같기 때문이다.
숫자를 나누면 「지금 나를 기다리는 게 몇 개냐」가 흐려진다."*

정의는 `STATUS_ORDER` 딕셔너리 **하나**이고 순서도 '막힘'의 정의도 거기서 파생된다.
이 원칙은 **착수 4분 만에 실전 근거를 얻었다** — `statusOrder`가 이미 별개 리터럴 사본이었고,
웹의 상태 점 목록에는 `question`이 **빠져 있었다.** 세 번째 사본을 만드는 대신 서버가 파생해
내려주게 고쳤고, 사흘 뒤 「뒤에서 진행」을 추가했을 때 **웹·메뉴바 양쪽이 자동으로 따라왔다.**

> 단, 이 원칙에서 벗어나 있던 마지막 사본이 클라이언트의 `URGENT`였고 —
> 그게 정확히 **9/7 마지막 신고의 원인**이 됐다.

### 두 신호가 한 채널을 다투고 있었다

> **[9/2]** "이런 띠 색깔은 **cmux workspace 에 적용된 색상** 적용되도록 해줘."

왼쪽 띠 하나가 상태를 나르는 동안, 사용자가 cmux에서 워크스페이스마다 **직접 칠해 둔 색은
화면에 아예 없었다 — 수집조차 안 하고 있었다.** (그룹 9개는 색이 전부 비어 있었지만
**워크스페이스는 78개 중 56개가 색을 갖고 있었다.**)

자리를 나눴다: **왼쪽 띠 = 사람이 칠한 색**(*이게 어느 일이냐*) /
**배경 옅은 물듦 = 상태**(*지금 돌고 있나*).

> *"「이게 어느 일이냐」와 「지금 돌고 있나」는 서로 다른 질문이라 **한 자리에 겹쳐 놓으면
> 둘 다 못 읽는다.**"*
> *"유휴에 물을 들이지 않는 건, 78장 중 대부분이 유휴라 거기까지 칠하면
> **'칠해진 것'이 신호가 되지 못하기** 때문이다."*

### 기능이 아니라 안내 문구가 없어서 아무도 안 쓴 기능

> **[9/2]** "웹 대시보드에서 (…) **검색창에서는 워크스페이스명도 검색되게 해줘.**"

검색 대상에 `workspaceTitle`이 **원래 들어 있었다.** 실측으로 확인까지 됐다.

> *"**못 찾으신 건 placeholder가 '탭·창·세션·프롬프트 검색'이라 시도할 이유가 없었기 때문**입니다."*

→ 문구를 고치고 그룹명·워크스페이스 설명까지 검색 대상에 넣었다.

### 명백한 설계 결함 — 다중선택이 불가능했다

> **[9/2 23:14]** "근데 워크스페이스든 윈도우든 클릭하는 순간 그 클릭한 것만 보여서
> **다른 걸 다중선택 하는 거 자체가 불가능한데?**"

에이전트가 인정했다 — *"맞다. **명백한 설계 결함이다** — 창 5를 누르는 순간 다른 창 헤더가
화면에서 사라지니 두 번째를 누를 대상이 없다. 주석에는 '여러 개를 눌러 더할 수 있다(OR)'고
써놓고 실제로는 불가능하다."*

**필터 로직은 처음부터 OR 다중선택이었다. 고칠 곳은 UI였다.**
→ 안 고른 것도 **지우지 않고 헤더만 흐리게 접어 둔다.**

자기 진단이 정확하다:
> *"제 검증이 창 필터를 건 상태에서 **그 안의** ws를 눌러 겹치기가 되는 것만 확인했다.
> 창→ws는 계층이 달라서 되고, 창+창·ws+ws는 안 되는 상황이었는데 전자만 보고 넘겼다.
> **같은 축을 두 번 누르는 걸 한 번도 시도하지 않은 게 구멍이었다.**"*

### "없다"고 단정한 것이 틀렸다

그룹 순서 변경 RPC가 없다고 결론 내리고 **화면 전용**으로 구현했다. 그러자:

> **[9/3 00:06]** "근데 그룹 순서 배치하는 게 **실제 cmux 환경에서는 적용이 안 되는데**"

> *"원하시는 건 실제 반영이니 방법이 정말 없는지 제대로 파보겠다.
> **`unpin`도 문서에 없다가 실제로 존재했으니 추측으로 단정하지 않겠다.**"*

결정적 발견: 그룹은 워크스페이스 목록 안에 **앵커 워크스페이스**로 존재하고 그 뒤에 멤버가 이어진다.
즉 **그룹 순서 = 앵커의 위치**. `workspace.group.move` + `before_group_id`로 **실제로 바뀐다.**

그리고 같은 조사에서 **자기 저장소의 주석에 답이 적혀 있는 걸 두 번 밟았다:**

> *"검증이 계속 어긋나서 코드를 의심했는데, 원인은 **브라우저가 옛 `nav.js`를 들고 있던 것**이었다.
> 이 저장소에는 이미 `NoCacheStatic`이 있었고 **그 주석에 답까지 적혀 있었다.**
> 나는 그걸 안 읽고, 한술 더 떠 **똑같은 문제를 해결하는 미들웨어를 중복으로 추가**했다."*

### 77개 중 1개가 이상하다고 76개를 못 보면 안 된다

> **[9/3]** "cmux 관제실 메뉴바에서 이렇게 **갱신 실패**가 떠서 종료 눌렀는데
> **내가 다시 켤 수는 없는건가?**"

탭 하나의 `lastActivity`가 `null`인데 Swift 모델이 필수 `Double`로 선언돼 있어
**응답 전체 디코딩이 실패**했다.

> *"**77개 중 1개가 이상하다고 나머지 76개를 못 보는 건 이 도구의 목적에 정확히 반한다.**"*

→ 탭을 **한 장씩** 디코딩, 필수 필드를 **둘만**(`surfaceId`·`status`) 남기고, 버려진 탭이 있으면
팝오버에 **"탭 N개는 형식이 어긋나 읽지 못했습니다"**를 적는다.
*"조용히 사라지면 왜 안 보이는지 영영 모르니까요."*

켜고 끄는 문제도 같이 해결했다 — `/Applications` 설치 + LaunchAgent,
그리고 **종료 버튼 호버에 "다시 켜려면 Spotlight에서" 안내**를 붙였다.

### 메뉴바에 놓는 그림은 뜻보다 시스템 아이콘과의 구별이 먼저다

> **[9/3]** "cmux mini map 메뉴바가 **갑자기 이렇게 나오네.**" (달이 두 개)

중복 실행이 아니었다. **집중 모드가 켜져 있어 macOS가 달 아이콘을 띄우는데, 그때 미니맵이

### 다섯 번째 상태 — 「뒤에서 진행」

> **[9/4]** "이렇게 되는 경우, 즉 **답은 일단 끝났는데 백그라운드에 뭔가를 돌리면서 그 상태를
> 계속 추적하고 다음 작업을 기다리는 경우**에도 따로 감지가 가능한지"

`run_in_background` 셸은 claude의 직계 자식 `/bin/zsh -c …`로 남는데, **전경 Bash도 똑같이 생겨서
프로세스만으로는 못 가른다.** → 판정을 좁혔다:

> **"턴이 이미 끝난 탭(대기)인데 셸이 살아 있다 = 뒤에서 진행 중"**
> *"셸 개수라는 신호는 **그 자체로는 아무 뜻이 없고 대기 상태와 만났을 때만 의미가 생긴다.**"*

상태 체계에서의 자리는 `running`과 `waiting` **사이**다:
> *"`running` 보다 아래인 이유: 지금 이 순간 내가 볼 것은 없다(내가 없어도 진행된다).
> `waiting` 보다 위인 이유: 그건 **완전히 멈춘** 것이고 이건 곧 다시 움직인다 —
> 게다가 **끝나면 사람이 한 번 찔러 줘야 다음이 이어지므로, 그냥 대기와 섞으면 방치된다.**"*

색에서 사고가 하나 있었다. 처음 쓴 `--gold`는 **이름과 달리 채도 낮은 베이지**라 20%로 깔아도
어두운 배경에서 회색으로 묻혔다(옆의 `running` 초록은 13%로도 뜬다 — 채도가 높아서).
→ `--lemon`을 새로 정의하고 **`amber`(권한 대기)와 일부러 갈랐다** —
*"둘 다 노랑 계열이지만 급한 정도가 정반대라 — 하나는 '내가 안 보면 0이 진행되는' 상태고
다른 하나는 '**내가 없어도 진행되는**' 상태입니다."*

**자기 한계도 명시했다** — ① 전경 명령이 도는 동안에는 알 수 없다(턴이 끝나야 드러난다, 대신 오탐 0).
② **서브에이전트는 안 잡힌다**(지금 규칙은 셸만 센다).

### 「모니터이」 — 조사 하드코딩 전수 QA

> **[9/5]** "이렇게 나오는데 조사가 "이" 가 아니라 "가" 가 되어야지. (…)
> **혹시 다른 거에도 이런 오류가 있진 않은지 확실하게 QA해.**"

1차 탐색 실패를 자백하고(`${...}` 직후만 본 패턴이라 **태그가 끼어든 경우를 놓쳤다** —
이미지의 케이스가 정확히 그것 `</b>이`) 전수로 다시 했다.
동적 값 직후에 한글이 붙는 지점 **54곳 전부** → 조사가 붙는 곳 4곳, **실제 버그 3곳.**

`josa()` 유틸은 한글이면 받침을 계산하고, **한글이 아니면 읽는 소리로 가른다** —
숫자는 발음표, 영문은 `a·i·o·u·y`로 끝나면 받침 없음.
→ `lifecycle`("라이프사이클") 받침 있음, `Safari`("사파리") 없음.

단위 테스트 14건 중 하나가 실패했는데 **테스트가 틀렸다**("삼"은 받침이 있으니 `3이`가 정확).

### 마지막 신고 — 초록이 주황보다 아래

> **[9/7 16:15]** "지금 진행되고 있는 세션(초록색)이 왜 **이미 끝난 세션(주황색)보다 아래에** 있어?"

버그가 둘이었다.

① `cmux 배치순` 모드가 그룹을 **앵커 인덱스로만** 줄 세워 급함을 전혀 안 봤다.

| 창 7의 그룹 | cmux 배치 위치 | 상태 |
|---|---|---|
| INBOX | **1번** | 대기 4 · 유휴 18 |
| 개인·생활 | **23번** | **작업중 1** |

→ 급한 게 든 그룹을 위로, 그 밖은 배치순. 급한 게 없으면 순수 배치순이라
**끌어서 맞춰 둔 순서는 그대로 보인다.**

② 클라이언트가 "최근순보다 앞에 두는 상태"를 **서버와 별개로** 들고 있었는데
(`URGENT` — 위에서 말한 마지막 사본), 사흘 전 「뒤에서 진행」을 추가하면서 **이쪽을 안 고쳤다.**
그래서 뒤에서 셸이 도는 탭이 **유휴와 같은 층**에 있었다.

**왜 정본을 그대로 못 쓰는지도 설계 의도로 남았다** — *"이 목록은 서버의 `statusOrder`를
그대로 쓸 수 없다. **대기·유휴·판정불가는 일부러 같은 층으로 묶어 최근순에 맡기는 설계**다.
대신 서버에 상태를 추가하면 여기도 봐야 한다는 경고를 주석으로 남겼다."*

자백 한 줄도 있다 — *"이 배치순 모드는 **그룹을 한 번 끌면 자동으로 켜집니다** …
의도해서 켠 게 아니라 그때 딸려왔을 수 있고."* 나흘 전 새벽의 드래그가 이 신고를 만들었다.

## 「막힘 강조」 4번의 반복

같은 밤 **35분** 안에 커밋 네 개가 나왔다. UI/UX를 어디까지 파는지 보여주는 대표 사례다.

| 커밋 | 사용자가 한 말 | 무엇을 고쳤나 |
|---|---|---|
| **1번째** | "자물쇠 표시되는 (…) 그거는 **탭 자체가 통통 튀는 느낌**으로 하이라이트가 되면 좋겠어요." | 없던 것을 만듦. `cubic-bezier(.34,1.56,.64,1)` — **"1.56이 '통통'이다"**(끝에서 살짝 넘어갔다 돌아온다) |
| **2번째** | "**채워진 색상이 약간 진해지는 효과**가 있으면 좋겠고, 움직임이 조금 더 **다이나믹**하면 좋겠어." | 색 펄스 + **이중 바운스**. 올라갈 때/내려올 때 이징을 나눔 — "등속으로 오르내리면 '통통'이 아니라 '**둥둥**'이 된다" |
| **3번째** | "통통 튀다가 **잠깐 멈추고** 다시 하고 이러는데" | 궤적이 **55% 동작 + 45% 정지**였다(주기 1.9s 중 0.86s가 통짜 정지). 세 번의 뜀이 주기 전체를 채우게 |
| **4번째** | "**3번 튕긴 다음에 멈췄다가 다시 3번 튕기고** 이런 식으로 되는데" | **직전 수정이 틀렸다** ↓ |

### 3번째 → 4번째가 핵심이다

세 번째에서 정지 구간이 0%임을 CSSOM으로 **측정해 "해결"이라고 판단했다.**
그런데 사용자는 여전히 멈춤을 봤다.

> *"**직전 수정이 틀렸다.** 나는 키프레임에서 정지 구간을 지웠고 '연속한 두 키프레임 사이에
> 위치·색이 모두 그대로인 구간 0%'를 측정해 해결했다고 봤다. 그런데 사용자는 여전히 멈춤을 봤다 —
> **내 측정이 틀린 것을 재고 있었다.**
>
> 진짜 원인: 감쇠가 너무 가팔랐다. 5.5 → 2.8 → **1.2px**. 마지막 뜀 1.2px는(이 맥은 동작 줄이기가
> 켜져 있어 실제로는 0.45px였다) **눈에 안 보인다.** 키프레임상 '움직이는 중'이어도
> **보는 사람에게는 정지다.** 기준은 '움직이고 있다'가 아니라 **'움직이는 게 보인다'** 여야 했다."*

그리고 판정 기준을 숫자로 못박았다 — *"실측 뜀 높이 3.3 / 2.52 / 1.92px — **최소가 1.92px로
1px 선을 넘는다**(이번 버그의 판정 기준). 동작 줄이기에서도 **더 줄이지 말 것.**"*

### 이 4연타에서 나온 기술 함정 셋

1. **`transform`은 쌓임 맥락을 만든다.** 카드 hover 설명(`z-index:40`)이 부모 transform에 갇힌다.
   추측하지 않고 **재현해서 쟀다** — 대역 요소를 넣고 다음 카드와 겹치는 지점에서
   `elementFromPoint`로 물었다. → `:not(:hover)` 가드
   (**"안 볼 때만 튀고, 보려는 순간 멈춘다"** — 읽으려고 커서 올린 카드가 흔들리면 읽기 힘들다).
2. **커스텀 프로퍼티는 등록해야 보간된다.** 등록 안 한 `--tint`는 문자열로만 다뤄져 중간값이 없다.
   `@property --tint{syntax:'<color>'}`.
   **검증 방법 자체가 한 번 틀렸다** — `CSS.registerProperty` 예외로 판정하려 했는데
   **WebKit은 CSS로 등록된 프로퍼티도 JS 재등록을 허용해 예외를 안 던진다.**
   → 캐스케이드로 직접 갈랐다(인라인으로 자홍을 강제 주입했는데도 computed가 키프레임의 amber면
   애니가 실제로 그 변수를 몰고 있다는 증거).
3. **키프레임 두 벌을 한 벌로 합쳤다.** 두 벌이던 탓에 이번 버그를 **한쪽에만 고칠 뻔했고**,
   정작 사용자가 보던 것은 **값이 더 작은 쪽**이라 증상이 더 심했다.

### ⚠️ 네 커밋 모두 "못 봤다"

> *"**튀는 모습 자체는 이 환경에서 검증하지 못했다.** cmux browser 서피스는 프레임을 안 그려
> 애니메이션 타임라인이 멈춰 있다(CSS transform·opacity·Web Animations 세 방식 모두
> `currentTime` 0). 확인된 것은 '**올바른 애니메이션이 올바른 카드에만 등록됐다**'까지다."*

**즉 이 4연타는 에이전트가 눈으로 못 보는 것을 사용자의 눈만으로 네 번 왕복해 맞춘 기록이다.**
세 번째에서 잘못된 측정을 신뢰한 것도 이 제약의 직접적 결과다.

> *"박준님이 실제로 보고 계시니(제가 못 보던 부분) **그 관찰이 정확한 근거입니다.**"*

(이 저장소의 README에 실린 바운스 GIF는 그 뒤에 나온 방법으로 찍었다 —
`animation-play-state: paused` + 음수 `animation-delay`로 **키프레임 위치를 하나씩 고정 렌더**해
24장을 이어 붙였다. WKWebView가 타임라인을 안 돌려도 **특정 프레임은 그린다.**)
